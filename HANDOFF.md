## 📋 Synopsis

KYA ("Know Your Agent") is a TypeScript/Hono service that provides blockchain wallet identity attestation and sanctions screening. It was built through workboard cards where multiple sub-agents contributed modules.

### Completed Modules (Production-Ready)

| Module | What It Does | Files |
|--------|-------------|-------|
| **Algorand Wallet Analysis** | SDK client, transaction history, sibling wallet discovery, wallet graph, in-memory caching | `src/algorand/client.ts`, `src/services/transactionHistory.ts`, `src/services/siblingDiscovery.ts`, `src/graph/walletGraph.ts`, `src/cache/inMemoryCache.ts` |
| **Sanctions Screening** | OFAC SDN integration (19,188 entries), Jaro-Winkler + Levenshtein fuzzy matching, audit log, watchlist updater | `src/services/screening.ts`, `src/services/ofac.ts`, `src/services/resolution.ts`, `src/services/audit.ts`, `src/services/watchlist-updater.ts` |
| **Human Verification** | Off-chain identity binding — attempt/claim stores (in-memory + Supabase), email provider, provider registry, service orchestrator | `src/verification/service.ts`, `src/verification/providers/email-provider.ts`, `src/verification/provider-registry.ts`, `src/verification/claim-store.ts`, `src/verification/in-memory-claim-store.ts`, `src/verification/attempt-store.ts` |
| **Karma Ledger** (schema only) | Supabase schema: 4 tables, RLS, 6 RPC functions, test suite. SQL files were generated by a sub-agent but **not persisted to disk** | `karma-ledger/schema/001_karma_ledger.sql` — *missing, needs recreation* |

### Incomplete / Stuck Modules

| Module | Issue |
|--------|-------|
| **A2A API Design** | 114+ repeated sub-agent failures — spec never materialized as code. Needs a fresh approach with a capable model. |
| **Deployment (OCI)** | Dockerfile + nginx.conf exist in git but the workboard card has been in a READY loop with zero progress. Dockerfile needs review to match current source structure. |

## 🔧 What Needs To Happen Next

### 1. Reunite the Karma Ledger Schema
The Karma Ledger Supabase schema was generated by a sub-agent but **the files were never written to disk**. You need to either:
- Find the original artifacts in conversation history (search for "Karma Ledger — Supabase Schema" workboard card `0a37c8ef`)
- Recreate the schema based on the card notes: 4 tables (app_registrations, agent_profiles, karma_events, karma_balances), RLS policies, 6 RPC functions, auto-creation trigger

The schema should go in `karma-ledger/schema/001_karma_ledger.sql` and be tested.

### 2. Fix the Deployment Card
The Dockerfile and nginx.conf in git are stale — they don't match the current source structure. The service now has:
- Multiple route modules (screening, wallet-analysis, verification)
- A full verification service with stores
- Environment-dependent config (Supabase optional, Algorand optional)

The deploy process needs to be reworked to reflect the current architecture. Consider:
- Multi-stage Dockerfile (build → runtime)
- Proper Supabase env config
- Health check that validates watchlist loading
- nginx reverse proxy for the Hono server

### 3. Build the A2A API
This is the highest-value missing piece. The A2A (Agent-to-Agent) protocol spec was never realized. A capable model should:
- Design the A2A API based on the existing modules
- Create proper TypeScript interfaces
- Implement the service layer
- Write comprehensive tests

## 🏗 Architecture Overview

```
src/
├── index.ts              — Package exports (wallet analysis domain)
├── app.ts                — Hono app entry (all routes mounted)
├── types/index.ts        — Shared types
├── utils/crypto.ts        — Crypto helpers (key gen, sign/verify)
│
├── algorand/
│   └── client.ts          — Algorand SDK client (350 lines)
│
├── cache/
│   └── inMemoryCache.ts   — TTL cache with stats
│
├── graph/
│   └── walletGraph.ts     — Directed graph for wallet relationships
│
├── routes/
│   ├── screening.ts        — Sanctions screening endpoints
│   ├── wallet-analysis.ts  — Wallet analysis endpoints
│   └── verification-routes.ts — Verification HTTP routes
│
├── services/
│   ├── screening.ts        — Screening engine
│   ├── ofac.ts             — OFAC SDN list management
│   ├── resolution.ts       — Wallet → owner resolution
│   ├── audit.ts            — Audit logging
│   ├── watchlist-updater.ts — Watchlist refresh
│   ├── transactionHistory.ts — Transaction history
│   ├── siblingDiscovery.ts  — Sibling wallet discovery
│
└── verification/
    ├── service.ts           — Verification orchestrator
    ├── types.ts             — Verification types
    ├── attempt-store.ts     — Supabase attempt store
    ├── claim-store.ts       — Supabase claim store
    ├── in-memory-store.ts   — In-memory attempt store
    ├── in-memory-claim-store.ts — In-memory claim store
    ├── provider-registry.ts — Provider registry
    └── providers/
        └── email-provider.ts — Email verification provider

__tests__/screening.test.ts  — 35 screening tests
test/verification.test.ts    — 26 verification tests
tests/complete.ts            — Integration test runner
test/run-tests.ts            — Full test runner
```

## 📝 Notes

- The service is **modular** — each domain (algorand, screening, verification) can be used independently
- Store injection is now supported for testing (`VerificationService` accepts `claimStore` and `attemptStore`)
- The verification service supports both Supabase and in-memory backends
- Watchlist data loads from OFAC.gov on startup, cached to disk
